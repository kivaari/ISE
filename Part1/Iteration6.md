# Итерация 6: Демонстрация прототипа и сквозная трассировка требований

В ходе 6-й итерации была завершена разработка полноценного рабочего прототипа системы. Реализованы ключевые сценарии взаимодействия, интегрирована бизнес-логика эскроу-платежей, реализован сбор и анализ телеметрии, а также проведена сквозная трассировка требований от бизнес-целей до строк кода и структур данных.

---

## 1. Разработка и демонстрация прототипа

### 1.1. Реализация ключевых сценариев использования

Прототип реализован в виде Full-Stack приложения (Backend: Go/Gin/PostgreSQL/Redis, Frontend: Vanilla JS/Chart.js).

#### Сценарий «Клиент: Аренда вычислительных мощностей»

1. Клиент просматривает каталог доступных нод (данные кэшируются в Redis для скорости).
2. Выбирает сервер, указывает срок аренды. Инициируется бронирование.
3. **Бизнес-логика:** Средства списываются с баланса клиента и перемещаются в `frozen_amount` (эскроу). Нода меняет статус на `busy`. Генерируются SSH-доступы.
4. Клиент запускает сессию, видит таймер обратного отсчета и графики телеметрии в реальном времени (CPU, RAM, GPU, Disk I/O).
5. По завершении таймера телеметрия сохраняется в БД, эскроу закрывается, 95% суммы поступает на баланс поставщика.

#### Сценарий «Клиент: Разрешение инцидента (Спор)»

1. При возникновении проблем клиент нажимает «️ Connection trouble».
2. Сессия замораживается, статус аренды меняется на `dispute`. Текущие метрики сохраняются в `metrics_snapshots` для разбора.
3. Клиент может общаться с поставщиком в чате.

#### Сценарий «Поставщик: Мониторинг и управление»

1. Поставщик подключает ноды с случайными характеристиками.
2. Видит дашборд со своими серверами и историей их аренд (аккордеон).
3. Может раскрыть любую аренду, посмотреть статус, вердикт арбитража и загрузить графики телеметрии (Lazy-load).

#### Сценарий «Арбитр: Разрешение споров»

1. Арбитр видит список открытых споров.
2. Открывает детали: видит характеристики ноды, чат участников и графики телеметрии перед сбоем.
3. Выносит вердикт (`refund` / `pay_provider`). Бизнес-логика эскроу автоматически распределяет заблокированные средства.

### 1.2. Обработка данных и взаимодействие с внешними системами

- **Кэширование (Redis):** Каталог нод синхронизируется с PostgreSQL в Redis (`syncCatalogToRedis`). Это имитирует высоконагруженный внешний API каталога и обеспечивает быстрый отклик UI (`updateProviderNodeStatuses` работает без деградации).
- **Идемпотентность:** Операции с эскроу (`escrow_transactions`) используют `idempotency_key` для защиты от дублирования платежей при сетевых сбоях.
- **Поллинг и Real-time:** Фронтенд обновляет каталог и статусы нод каждые 3 секунды с оптимизацией рендера (Update DOM instead of Re-render), а графики обновляются раз в секунду через `requestAnimationFrame`.

### 1.3. Пользовательские интерфейсы

- Реализован Apple-style UI Kit с использованием шрифтов Unbounded и Inter.
- Интерфейсы адаптированы под роли: минималистичный каталог для клиента, технический дашборд с телеметрией для поставщика, модальный интерфейс арбитража для админа.

## 2. Сквозная трассировка требований

### 2.1. От бизнес-целей к функциональным требованиям

| Бизнес-цель (Итерация 3) | Функциональное требование (Итерация 3) | Реализация в прототипе (Итерация 6) |
|:---|:---|:---|
| Обеспечение доверия между сторонами | Безопасное хранение средств до подтверждения качества услуг | Реализован паттерн "Эскроу" (таблицы `wallets`, `escrow_transactions`, логика `hold/capture/refund` в транзакциях Go) |
| Прозрачность причин сбоев | Сбор и хранение объективных метрик работы сервера | Генерация телеметрии на клиенте, запись в `metrics_snapshots`, визуализация через Chart.js при разбирательстве |
| Снижение финансовых рисков поставщика | Автоматическое распределение средств при успешном завершении | Триггер `CompleteSession` автоматически высчитывает комиссию 5% и переводит 95% на баланс провайдера |

### 2.2. От требований заинтересованных лиц к сценариям

| Заинтересованное лицо | Потребность | Сценарий использования (Use Case) | Реализация в UI/UX |
|:---|:---|:---|:---|
| **Клиент** | Вернуть деньги, если сервер сломался | UC-4: Разрешение инцидента | Кнопка "Connection trouble", статус `dispute`, визуализация возврата (синий бейдж "Возврат") |
| **Поставщик** | Доказать, что сервер работал корректно | UC-5: Просмотр истории аренд | Аккордеон с историей аренд у провайдера, доступ к телеметрии завершенных сессий, зеленый бейдж "Спор выигран" |
| **Арбитр** | Принять взвешенное решение на основе фактов | UC-6: Арбитраж | Окно детализации спора: чат + 4 графика метрик (CPU/RAM/GPU/Disk) перед сбоем |

### 2.3. От атрибутов качества к архитектурным решениям

| Атрибут качества | Архитектурное решение | Обоснование |
|:---|:---|:---|
| **Надежность (Reliability)** | Использование транзакций БД (`db.Begin()`, `tx.Commit()`) при работе с кошельками и эскроу | Гарантирует атомарность: баланс не спишется, если не создастся бронирование |
| **Производительность (Performance)** | Внедрение Redis для кэширования каталога; Оптимизация DOM на фронтенде (функция `updateProviderNodeStatuses` вместо `innerHTML`) | Снижение нагрузки на PostgreSQL, устранение "мигания" UI и разрушения графиков при поллинге |
| **Расширяемость (Extensibility)** | Разделение бэкенда на модули (`handlers_booking`, `handlers_admin`, `storage`), фронтенда на ES-модули (`ui.js`, `charts.js`, `api.js`) | Легкое добавление новых ролей, эндпоинтов и логики без изменения существующего кода (SOLID) |
| **Безопасность (Security)** | Изоляция SSH-доступов (генерация случайных паролей), паттерн эскроу (клиент не платит напрямую провайдеру) | Исключение мошенничества со стороны провайдера (невозможно получить деньги минуя эскроу) |

### 2.4. Трассировка данных

- **`nodes` + `hardware_specs`** → Используются в каталоге (`GetCatalog`), при генерации нод (`ConnectNode`) и при арбитраже (`GetDisputeDetails` для вывода спек сервера).
- **`wallets` (balance/frozen_amount)** → Ядро финансовой системы. Модифицируются в `TopUp`, `BookNode` (hold), `CompleteSession` (capture), `ResolveDispute` (refund/partial capture).
- **`telemetry_sessions` + `metrics_snapshots`** → Создаются при старте аренды, заполняются метриками при инциденте или успешном завершении (сохранение истории), читаются арбитром и поставщиком для графиков.
- **`disputes`** → Связывает бронирование, статус спора и вердикт. Влияет на то, какая бизнес-логика сработает в `ResolveDispute`.
